What happens at every stage

1. Upload and run record

The platform opens an ingestion run before parsing. It records who submitted the source, which profile applied, the fingerprint, and the final outcome.

2. Validate before trust

Every source is converted to a canonical shape. Invalid identity, conflicting column definitions, or an unexpectedly large source change are quarantined or held.

3. LLM call: metadata enrichment

Only permitted metadata is sent to the LLM through an audited structured call. It may suggest that transaction_amount is a currency amount; it cannot make that claim authoritative.

4. Searchable graph

Accepted tables and columns become nodes; containment and declared relationships become graph edges. This enables search, lineage, and discovery.

5. LLM call: candidate context

AI-assisted stages may propose table semantics, join candidates, or semantic bindings. These are clearly labelled proposals and cannot bypass governance.

6. Human approval and readiness

Data owners approve the facts and relationships that may be used operationally. The platform rebuilds projections, detects drift, and closes the ingestion run honestly.

Example: transaction catalog upload

A human uploads a file with transactions.transaction_amount and transactions.booking_timestamp. Validation confirms the column identities. The pink LLM stage proposes “currency amount” and “event time” from approved metadata. A data owner confirms the relevant semantics and relationship to accounts. Only then can a feature such as “30-day transaction value” use this context safely.

Example outcomes

GOOD / ACCEPTED

Clear source metadata

transactions.transaction_amount has one valid identity, declared type decimal, and a consistent source definition. It enters the graph and source-evidence layer.

QUARANTINED

Conflicting catalog rows

The same column appears twice: once as decimal and once as varchar. Both claims are retained for review, but no operational type fact is created.

REJECTED

Unsafe feature candidate

A proposed feature uses a post-outcome transaction timestamp for a churn model. The deterministic feature checks reject it for temporal leakage; it cannot become a contract.

TO BE VALIDATED

Data-dependent claim

A candidate assumes customer_id is unique at the required grain. Metadata alone cannot prove it, so the platform records an external validation requirement rather than claiming success.
